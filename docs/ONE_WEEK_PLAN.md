# 一周冲刺计划

目标不是一周内完成生产系统，而是做出一个面试官可以验证技术判断的项目版本。

## 时间假设

- 每天投入 4 至 6 小时。
- 每天结束必须有一个可运行、可检查的交付物。
- 功能优先级高于界面美化，证据优先于功能数量。

## 每日安排

| 时间 | 核心任务 | 验收物 |
|---|---|---|
| 第 1 天 | Git 基线、CI、敏感文件检查、学习文档 | 可运行 CI、初始提交、提交规范 |
| 第 2 天 | 登录身份与用户隔离 | 用户身份不再由业务页面随意伪造 |
| 第 3 天 | 意图路由与确定性工具策略 | 知识问题强制调用 RAG |
| 第 4 天 | 结构化证据、引用校验、索引重建 | 回答来源可验证，索引状态可恢复 |
| 第 5 天 | 30 条评测集和指标结果 | 工具准确率、Hit@3、安全通过率 |
| 第 6 天 | 重试、请求追踪、连续操作 E2E | 失败可见，没有无限等待 |
| 第 7 天 | 部署、演示视频、简历和模拟面试 | 可访问地址和两分钟讲解 |

## 最终验收线

- Git 至少包含 6 个有意义的提交。
- CI 中的依赖检查、编译和 pytest 全部通过。
- 知识类用例 RAG 调用率为 100%。
- RAG Hit@3 不低于 90%。
- 安全类用例通过率为 100%。
- 引用正确率人工抽检不低于 95%。
- 连续点击两个快捷问题能完成两次独立回答。
- 超时或错误在 60 秒内对用户可见。
- README 包含真实指标、架构、限制和改进计划。
- 能不依赖稿子讲清一次成功请求和一次失败请求。

## 本周明确不做

- PDF 上传和多格式知识库管理。
- 语音输入、多 Agent 协作和复杂动画。
- Kubernetes、微服务拆分和向量数据库迁移。
- 为了展示功能数量而增加未评测的页面。

## 每天复盘问题

1. 今天新增的能力由什么测试或指标证明？
2. 如果面试官问“为什么这样做”，我能否说出取舍？
3. 今天是否引入了新的安全、成本或延迟风险？
4. 哪项功能只是看起来完整，实际仍依赖模型自觉？
5. 明天开始前，最重要的未解决问题是什么？
