# 面试讲解指南

## 一句话定位

“我做了一个面向家电电商客服的 Agent 工作台，核心不是聊天，而是让模型在受控权限下调用知识库、订单和使用记录工具，并且能通过执行轨迹和离线评测定位问题。”

## 两分钟项目介绍

### 背景

家电客服同时面对商品知识、故障排查、订单物流和个人使用报告。普通 RAG 只能回答文档问题，不能查询订单，也无法把用户当月使用数据组织成报告。

### 我的方案

1. 用 LangGraph ReAct Agent 负责开放问题的工具选择。
2. 用 Chroma 保存家电知识库，检索结果带来源，提示词明确把文档当作不可信数据。
3. 把当前用户、城市和报告月份作为运行时上下文注入工具，并在订单和使用记录层再次校验归属。
4. 用中间件处理工具耗时、模型调用日志和报告场景提示词切换。
5. 前端同时消费 LangGraph 的 token 流和状态流，展示真实回答与工具轨迹。
6. 建立 Hit@K 检索评测和 pytest 回归测试。

### 结果

当前覆盖 10 个演示用户、12 个月使用记录、6 个家电知识文件和 10 条检索评测用例。基础测试不需要 API Key 即可运行。

## 简历写法

不要把项目写成“使用 LangChain 做了一个智能客服”。建议写结果和工程问题：

- 设计家电客服 Agent，联合 RAG、订单查询与用户使用记录工具，实现知识问答、订单状态和月度报告三类任务。
- 通过 OIDC 可信登录态、服务端邮箱映射和工具层资源归属校验实现用户隔离；本地演示只使用服务端固定用户，页面不能伪造 `user_id`。
- 构建带来源引用的 RAG 链路和 10 条 Hit@K 评测集，将检索质量与最终生成质量分开定位。
- 同时消费 token 流与工具事件流，实现可观测执行轨迹；补充消息清洗、CSV 数据服务和端到端页面测试。

## 面试官最可能追问的问题

### 1. 这是 Agent 还是工作流？

回答要点：知识问答是开放式步骤，适合 ReAct；报告生成步骤固定，适合工作流。项目采用混合架构。生产上我会把退款、价格承诺等高风险动作从自主 Agent 中拆出来，使用显式状态机和人工确认。

不要回答“Agent 比工作流高级”。Agent 只是把决策交给模型，成本和不确定性更高。

### 2. 为什么不直接把所有资料塞给模型？

回答要点：上下文窗口、成本和可追溯性都不允许。RAG 先缩小证据范围，来源列表还能用于人工核查。当前 chunk 是 500、overlap 20，偏小的 chunk 有利于定位，但可能丢上下文，所以后续应做更系统的 chunk size 对比。

### 3. 怎么防止模型读别人的订单？

回答要点：不依赖系统提示词。登录态先由 OIDC 验证，服务端把可信邮箱映射为业务用户；工具执行时再从 `ToolRuntime.context` 取当前用户，并与订单或记录的归属做校验。越权和不存在返回同一种结果，避免资源枚举。

### 4. 你的会话记忆怎么做的？

回答要点：当前是 session-level 的最近 12 条有效消息，过滤 system/tool 等角色，防止前端注入消息类型。它不是长期记忆。生产环境要引入 checkpointer、用户隔离的 thread_id、过期策略和隐私清理。

### 5. 为什么流式输出要同时看 messages 和 updates？

回答要点：`messages` 给最终回答 token，`updates` 给节点更新和工具调用结果。两者组合后，前端才能既显示回答，又显示“检索知识库、读取使用记录”等审计信息，不需要解析内部状态。

### 6. 怎么避免模型把思维链输出给用户？

回答要点：提示词禁止展示内部推理；产品只展示工具轨迹。思维链不是可靠的调试数据，也不应包含隐私或系统提示词，因此不作为产品功能。

### 7. RAG 的检索质量怎么证明？

回答要点：先把检索和生成拆开。检索层看 Hit@K、关键词覆盖率，生成层再看忠实度、引用正确率和任务完成率。当前 10 条用例只能做回归，不能证明线上泛化；下一步会扩充到多户型、多故障、多表述和负样本。

### 8. 如何防文档提示词注入？

回答要点：RAG 提示词明确把文档当不可信数据，忽略文档内改变角色和权限的指令；工具层有真实权限校验；不把密钥和内部配置放入上下文。提示词防御只能降低概率，不能替代工具和数据库权限。

### 9. 为什么选 Chroma？

回答要点：项目是单机演示，Chroma 部署简单、支持增量写入和元数据过滤。数据到百万级或多租户强隔离时，我会重新评估服务化向量库、索引成本和权限模型，而不是默认 Chroma 能覆盖生产。

### 10. 工具调用失败了怎么处理？

回答要点：当前中间件记录工具名、参数键、耗时和异常，前端显示失败状态。生产上还需要超时、有限重试、熔断、幂等键和降级答复。不能无限自动重试，否则会放大费用和工具副作用。

### 11. 为什么测试不需要 API Key？

回答要点：把纯逻辑和外部依赖分开测。数据解析、用户隔离、消息过滤、事件流转换都可以确定性测试；页面冒烟只验证无 Key 时能正确提示。真实模型质量放在独立评测任务，不混进普通 CI。

### 12. 这个项目目前最大的不足是什么？

回答要点：缺少生产级身份认证、持久化记忆、真实订单系统和更大规模评测。演示数据是本地 CSV，所以它能证明架构和工程边界，不能证明线上业务规模。下一步优先补身份认证与端到端评测，而不是继续堆 UI 功能。

## 面试表达方式

使用“问题 - 方案 - 取舍 - 验证”四步：

1. 问题：客服问题跨知识、订单、个人数据，单纯问答无法闭环。
2. 方案：Agent 负责选择工具，中间件负责场景，工具负责权限。
3. 取舍：开放式问答用 Agent，高风险流程用确定性编排。
4. 验证：用权限测试、页面测试和 Hit@K 检索评测证明关键假设。

## 不要这样说

- “用了 LangChain 所以是 Agent。”
- “提示词里写了不能越权，所以安全了。”
- “RAG 就不会幻觉。”
- “流式输出就是性能优化。”
- “评测 10 条命中率 100%，所以线上准确率 100%。”

## HR / 行为面试角度

准备一个 60 秒版本和一个 2 分钟版本。重点体现：

- 你能把模糊需求拆成知识问答、订单、报告三类任务。
- 你知道大模型不稳定的地方，并主动加权限、评测和日志。
- 你敢说明限制，不把演示项目包装成生产系统。
- 你关注业务结果：减少人工查资料、缩短售后定位时间、提升报告生成效率。
